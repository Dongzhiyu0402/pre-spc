| 主题 | 结论 |
|------|------|
| 开源项目 | 无现成"中文论文查重引擎"可直接复用；paper_checking_system 思路最接近（连续字符串匹配=知网式片段匹配），但核心 DLL 未开源、C#/GPLv2 不可移植；可复用其"文本格式化 + 片段标红"思路与 TF-IDF/向量化脚手架 |

## 1. 开源项目调研结论

### 1.1 用户提到的项目

**PlagiarismDetection（harirakul/Plagiarism-Detection）**
- 技术：Python + Flask + NLTK，将输入文本与**网络文章**比对（websearch + TF-IDF 相似度），输出相似度百分比。MIT 协议，约 26 stars。
- 可复用点：TF-IDF + 余弦的工程脚手架、Flask 集成方式、报告展示思路。
- 不可用点：英文语料为主、无中文分词优化、依赖搜索网站 Cookie（不稳定、有 ToS 风险）、无片段级定位、无语料库比对能力。

**paper_checking_system（ye7love7 / dong03 等，多个 fork）**
- 技术：C# + C++，号称"一亿字次级论文库秒级查重"。核心算法是**连续相同字符串匹配**（超过阈值 10-16 字即判定重复），即与知网"13 字连续匹配"同源的片段级方法；报告标红导出 RTF。GPLv2 协议。
- 可复用点（思路层面）：**文本格式化流水线**（去摘要/目录/参考文献/非中文字符）、连续字符串匹配阈值设计、片段标红报告形态——这三条与知网查重的实际形态高度一致，是很好的产品行为参照。
- 不可用点：核心比对模块 `paper_check.dll` **未开源**（需商务购买）；C#/C++ 技术栈与我们（Python）不匹配；GPLv2 传染性对闭源/商业化不友好；无校准、无多平台方案、无 Web API 形态。

**plagiarism-detector（Karthik-02/plagiarism-detection）**
- 技术：Python + Streamlit + scikit-learn（CountVectorizer + cosine_similarity）+ docx2txt/PyPDF2 + 网页抓取。教学演示级。
- 可复用点：文档解析（docx/pdf→text）、两两相似度计算的简单实现。
- 不可用点：无中文优化、两两 O(n²) 无索引、无大规模候选召回、演示级质量。

### 1.2 补充调研的同类项目

**Plagiarism-Detector-Rust（SMS-COSMO）**
- 技术：Rust + jieba-rs + TF-IDF + Rocket + SeaORM，POST 文本入库并对库内已有论文算 top5 相似度。MIT。
- 参考价值：证明了"**jieba 分词 + TF-IDF + 库内比对**"这一最小流水线在中文场景的可行性；其"查重后是否入库（write 开关）"的 API 设计值得借鉴。

**PlagiarismDetector（liu-chun-wu，台湾中大）**
- 技术：Flask + React + Agentic RAG + EFK，做**中文论文 AI 生成/改写检测**（非文本相似度）。MIT。
- 参考价值：报告高亮片段交互、多 Agent 判别流程、EFK 日志架构可借鉴；但功能定位是 AI 检测而非重复率，不直接复用。

**PaperCheck（ye-guang-prog，Python）**
- 技术：声称 NLP 相似性检测 + 分段分析 + 多格式 + PDF 报告。0 star，README 不完整。
- 结论：低质量占位项目，不采用。

**paper-generate-check-system**
- **未能检索到该确切仓库名**（公开 GitHub 上无此名项目）。最接近的是 `paper_checking_system` 家族。
- 建议：请项目总监向用户核实该仓库的准确 URL；若不存在，以 `paper_checking_system` + 上述项目作为全部开源参照即可。

### 1.3 开源可复用性总评

| 项目 | 可复用点 | 不可用点 |
|------|----------|----------|
| paper_checking_system | 文本格式化流水线、连续匹配阈值、标红报告形态（思路） | 核心 DLL 闭源、C#/GPLv2、无 Web API |
| Plagiarism-Detection | TF-IDF 脚手架、Flask 集成 | 英文、依赖搜索 Cookie、无片段定位 |
| plagiarism-detector | docx/pdf 解析、余弦实现 | 演示级、O(n²)、无中文优化 |
| Plagiarism-Detector-Rust | jieba+TF-IDF 最小流水线、API 设计 | Rust 栈、无校准 |
| PlagiarismDetector | 片段高亮交互、EFK | AI 检测定位、非重复率 |

**结论：无现成可整体复用的中文论文查重引擎，需自研。** 自研引擎可站在"字符 n-gram 连续匹配（知网式）+ SimHash 召回 + MinHash 去重 + TF-IDF 特征"的组合之上，全部算法在 Python 生态均有成熟库（jieba / scikit-learn / datasketch / simhash）。

## 2. 查重算法选型对比（中文论文场景）

| 算法 | 原理 | 中文论文场景优势 | 劣势 | 本项目中角色 |
|------|------|------------------|------|--------------|
| 字符级 n-gram / 连续子串匹配（containment） | 将文本切为 n 字片段，统计命中片段占全文比例；知网即"13 字连续匹配" | **与知网行为最接近**；字符级免分词误差；天然支持片段级定位（报告高亮） | 对同义改写/句式变换不敏感 | **主引擎**（第一判据） |
| SimHash | 加权特征 → 64 位指纹，汉明距离判定近似 | 极快、内存小、适合全库预筛 | 粗粒度、无法定位片段、对局部抄袭召回弱 | **候选召回层**（先缩小比对范围） |
| MinHash + LSH | 集合签名压缩 + 局部敏感哈希，估计 Jaccard | 大规模语料去重与候选检索、可并行 | 文档级相似，片段定位需再配合 shingle | 语料库构建与去重 |
| TF-IDF + 余弦 | 词频加权向量空间模型 | 主题相似度信号好、可解释 | 分词质量敏感、对复制粘贴不敏感（被高频词稀释） | **校准特征**之一，非主判据 |
| 语义嵌入（BERT/句向量） | 深度模型编码句子语义 | 可识别改写 | 成本高、MVP 阶段引入 GPU/模型复杂度 | **二期候选**（P1 降重建议时评估） |

**选型结论**：
1. 主判据 = 字符级 n-gram 包含度（建议 n=2-6 多窗口 + 最长连续命中片段统计，模仿知网 13 字规则）。对中文免分词、对复制粘贴检出最直接、可输出命中片段做报告高亮。
2. 引擎流水线 = 文本清洗 → 分段 → 字符 n-gram 指纹 → **SimHash 全库召回候选** → 候选集内 n-gram 精算 → 命中片段聚合 → 输出"总相似度 + 片段 + 来源"。
3. 语料库构建期用 MinHash+LSH 做去重与近邻索引。
4. TF-IDF 余弦作为校准模型特征（衡量"主题相似"与"字面重复"的结构差异）。
5. 阈值策略：学术场景**宁高召回（低阈值）不漏报**，用校准层兜底绝对数值。

## 3. 中文语料库方案

| 语料 | 规模 | 版权 | 用途 |
|------|------|------|------|
| THUCNews（清华） | 74-84 万篇新闻，约 1.45-2.19GB | 免费供研究者使用（需登记下载）；原始新闻内容版权归原媒体 | 引擎基准测试、种子语料、校准样本补充 |
| LCSTS（哈工大） | 约 240 万条短文本摘要对 | 研究用途 | 短文本/句级指纹验证 |
| 中文维基百科 dump | 约 150 万词条，约 2.2GB（2025-09） | CC BY-SA 4.0（署名+相同方式共享） | 百科类种子语料、简繁归一后做指纹库 |
| 用户上传文档（脱敏+授权） | 随试点增长 | 需用户协议授权 | **最贴近论文分布的语料**，核心增量 |
| 学术论文/期刊库（知网/维普/万方） | 上亿篇 | **不可获取**（商业+版权） | 无 |

**方案**：
- 种子语料 = THUCNews + 中文维基（简繁归一），先跑通引擎与基准测试。
- 增量语料 = 用户上传文档，**脱敏 + 授权协议**后入库（产品已有此风险清单，务必落实）。
- 关键提醒：开源语料**不得作为对外宣称的"学术比对库"**；引擎报告措辞必须与"绝对等于知网"切割。
- 简繁归一工具：OpenCC；分词：jieba；指纹索引：PostgreSQL（见 §5）。

**根本性局限（必须接受）**：自研引擎的比对库规模远小于知网 → 自研绝对查重率系统性偏低 → 这**正是校准层存在的理由**，但校准只能缩小差距、不能消除；MVP 必须定位"相对风险提示 + 趋势预测"，UI 呈现置信区间（与 PM 的"精度达不到预期"风险项互相印证）。

## 4. 校准模型技术路线

### 4.1 可行性结论：可行，分三阶段演进

| 阶段 | 触发条件 | 模型 | 说明 |
|------|----------|------|------|
| 冷启动 | 配对样本 < 50 | 规则 + 常数偏移 | 用公开经验关系（如 PaperPass 与知网偏差）预设每组 (平台, 类型) 的初始偏移与上下界 |
| 线性回归 | 50 ≤ 样本 < 200 | 单特征/多特征线性回归 | 可解释、防过拟合；输出"预估区间 = 预测值 ± 残差带" |
| GBDT 迭代 | 样本 ≥ 200 | LightGBM（GBDT 回归） | 捕获非线性与特征交互；特征重要性可解释、可审计 |

### 4.2 特征设计（建议清单）

按文档级 + 引擎内部信号 + 平台元数据 + 结构工程四类：

1. **引擎内部信号**（核心）：
   - 各算法原始分：n-gram containment、SimHash 相似度、MinHash Jaccard、TF-IDF 余弦
   - 命中统计：命中片段总数、**最长连续命中片段长度**（最贴近知网 13 字规则的信号）、命中片段平均长度、命中来源数
2. **文档结构特征**：
   - 总字数、平均句长、段落数、参考文献占比、章节分布（摘要/引言/正文/结论/致谢分别的命中率）
3. **平台与类型元数据**：
   - 目标平台（知网/维普/万方，one-hot）、论文类型（本科/硕博/期刊）、学科类别（如有）
4. **工程化特征**：
   - 文本清洗质量分、语料库覆盖度（命中来源是否来自种子语料/用户库）

### 4.3 关键工程约束

- **按 (平台, 论文类型) 分桶建模**，不混训（知网/维普/万方算法与库差异大）。
- **回传报告标准化解析**是数据质量门禁：PDF/HTML/Word 报告 → 结构化提取（总重复率、各章节重复率、来源列表），解析失败样本人工标记不入训练。
- **数据飞轮闭环**：回传样本必须带"文档指纹版本 + 引擎版本 + 校准模型版本"元数据，防止模型与引擎错配。
- **精度目标**：MAE 收敛到 5% 以内（随样本增长），与 PM 大纲一致；未达标时 UI 放大置信区间，绝不虚假精确。
- 训练/推理均在 RQ worker 内进程完成（LightGBM 模型文件 + 定期重训任务），无需单独模型服务。

## 5. 技术栈选型结论（含版本锚定方向）

### 5.1 后端框架

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| **FastAPI 0.115+（推荐）** | ASGI 原生异步、Pydantic v2 校验、自动 OpenAPI、与 AI/ML 生态同栈、可复用引擎纯 Python 代码 | 生态较新 | ★★★★★ |
| Flask 3.x | 极简、生态成熟 | WSGI 同步、需手动集成文档/校验、异步要绕 | ★★★ |
| Django 5.x | 全栈内置 | 重、对纯 API + 异步任务场景过度设计 | ★★ |

**结论：FastAPI**（与 mvp-stack 矩阵的"AI 应用/API 服务"推荐一致）。

### 5.2 数据库

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| **PostgreSQL 16（推荐）** | JSONB、全文检索、扩展生态（未来 pgvector）、事务成熟、单机承载校内试点绰绰有余 | 运维比 SQLite 重 | ★★★★★ |
| MySQL 8 | 生态大、团队可能更熟 | JSON/全文/扩展弱于 PG | ★★★★ |
| SQLite | 零运维 | 并发写弱、不适合服务端多用户 + 任务队列 | ★★（仅桌面端离线缓存用） |

**结论：PostgreSQL 16**（服务端）；**SQLite** 仅用于 PyQt6 桌面端本地离线缓存。

### 5.3 任务队列

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| **RQ 2.x（推荐）** | 仅依赖 Redis、1 天上手、内置超时/重试、rq-dashboard 监控够用 | 不支持多 broker | ★★★★★ |
| arq | 原生 asyncio、极简 | 生态小、多 worker 启动要自管 | ★★★★ |
| Celery 6.x + Redis | 功能全、生态大、可扩展 | 组件多（worker/beat/flower）、对几百人试点**过度设计** | ★★★ |

**结论：RQ**。查重是耗时任务（1 万字 30 秒内），RQ + 单 Redis 完全满足校内试点；未来并发上来可平滑迁 Celery。

### 5.4 桌面端打包

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| **PyInstaller 6.x（MVP 推荐）** | 一键打包、文档多、问题好搜 | 体积大、启动慢、杀软误报 | ★★★★★ |
| Nuitka | 编译为机器码、启动快、体积小、源码保护强 | 需 C 工具链、配置复杂、构建慢、第三方库兼容要调 | ★★★ |

**结论：MVP 用 PyInstaller（onedir 模式 + 提交杀软白名单）**；正式发布期可评估 Nuitka 收尾优化。桌面端与 Web 端**共享同一套纯 Python 引擎代码**（引擎层与 UI 层隔离）。

### 5.5 Web 前端

- **React 18 + Vite + TypeScript + Ant Design 5**（工具型产品、表格/上传/报告组件开箱即用，MVP 速度优先）。
- **图标系统（锁定）：Lucide（MIT，lucide-react）**。
  - 理由：线条风格统一、1000+ 图标、MIT 可商用、React 生态 tree-shaking 友好、可与 AntD 组件并存（P0 规则：功能图标统一用 Lucide，不混用 AntD 图标）。
  - 桌面端同源：将 Lucide SVG 文件随 PyQt6 打包为资源，用 `QSvgWidget`/`QSvgRenderer` 渲染，保证 Web 与桌面**同一套图标、视觉统一**。
  - 备选（不采用）：Phosphor（风格偏重）、Tabler（风格偏实心）、Heroicons（官方绑定 Tailwind 感强）。
- 此锁定项已同步设计师，避免双端图标不一致。

### 5.6 版本锚定方向（Phase 1.5 钉死具体版本）

| PaperPass | **未检索到公开开发者文档** | 1.5-1.8 元/千字 | 仅产品网页/小程序 | 不可作为 API 接入 |
| PaperFree / PaperYY / 大雅 / CheckPass | 无官方文档；有非官方 RESTful 接口传闻 | 免费额度+按量 | 非官方、不稳定、ToS 风险 | 不采用 |
| 灰色渠道（87-149 元/篇的"知网内部版"） | — | — | 逆向/冒用资质 | **法律风险，明确禁止** |

**结论**：
1. **知网/维普/万方核心库对个人开发者不开放 API**，这是行业现实，短期内无法改变。
2. MVP **不做第三方 API 直连**，而是：保留**统一适配器接口**（平台枚举 + 认证 + 计费 + 限流），先用**模拟实现占位**（与 PM 大纲一致）。
3. 真正可行的路径恰是产品核心差异点：**用户自行去官方平台送检 → 回传真实报告 → 喂给校准模型**。这既合规（用户自己付费、自己拿报告）又支撑数据飞轮。
4. 若未来要接第三方：优先谈**万方个人开发者 API**（需实名+备案）或 **PaperPass 类平台的 to B 商务 API**（需商务洽谈），作为 P1 增强项。

## 7. 推荐架构（轻量自费 + 校内试点约束）

```
┌─ 桌面端（PyQt6，本地安装版）─────────────────┐
│  本地引擎（纯 Python，离线可用）             │
│  本地 SQLite 缓存（报告/用量）               │
│  在线同步（校准/账号/第三方占位）           │
└───────────────┬──────────────────────────────┘
                │ HTTPS
┌─ Web 端（React18 + Vite + TS + AntD + Lucide）┐
│  上传/报告/回传/用量                          │
└───────────────┬──────────────────────────────┘
                ▼
┌─ 后端（单台轻量云服务器 2C4G，Docker Compose）─┐
│  Nginx ─► FastAPI（REST /api/v1，JWT）        │
│      │                                        │
│      ├──► RQ Worker ──► 查重引擎（纯 Python）  │
│      │        │            │ n-gram 主判据     │
│      │        │            │ SimHash 召回      │
│      │        ▼            └ 语料库索引        │
│      ├──► Redis 7（任务队列）                  │
│      ├──► PostgreSQL 16                        │
│      │     users / orders / tasks / reports    │
│      │     calibration_samples / models        │
│      └──► 本地磁盘（文档原件，加密+定时清理）   │
│      └──► 校准层（LightGBM 分桶模型，worker 内）│
└────────────────────────────────────────────────┘
```

- **部署形态**：单台轻量云服务器（2C4G，约 ¥100-150/月）+ 域名 + SSL（约 ¥100/年），Docker Compose 一键编排。
- **异步化**：上传 → 建任务 → RQ 消费 → 查重（1 万字 30 秒内）→ 报告入库 → 前端轮询/推送。
- **多平台方案**：方案枚举（知网模拟/维普模拟/万方模拟/第三方占位）在配置中可增删；每个方案对应一组"引擎参数 + 校准模型桶"。
- **文档合规**：原件加密存储 + 30 天自动清理（对齐知网做法）；用户上传入库需授权协议 + 脱敏。
- **目录结构约束**：按 `references/01-standards/code-organization.md` 精神，单文件 ≤300 行、单一职责、入口只装配、按资源分包（users/checks/reports/calibration 等），Phase 1.5 输出可执行目录树。

## 8. 技术约束与不可行警告（必须知悉）

1. **【不可行】获取知网/维普/万方学术论文比对库**：非开放数据，版权 + 商业机密双重壁垒。→ 自研绝对查重率必然系统性低于官方；校准模型只能缩小差距不能消除；**MVP 定位必须收敛为"相对风险提示 + 趋势预测"**，UI 呈现置信区间，报告附免责声明。
2. **【禁止】承诺与知网结果一致**：技术不现实、法律上误导（产品层面已有免责声明，架构层不再重复建设"精确一致"承诺）。
3. **【禁止】接入灰色渠道 API**（"知网内部版" 87-149 元/篇等）：逆向工程、冒用资质，触犯《刑法》280 条及反不正当竞争风险。适配器仅接官方/合规渠道。
4. **【不可行】MVP 做语义级改写检测**：需深度模型与算力，超出轻量预算。用 n-gram 召回 + 片段级命中即可覆盖"复制粘贴"主场景；改写检测列入二期（P1 降重建议）评估。
5. **【风险】开源语料版权**：THUCNews 免费供研究但原始内容版权归媒体、LCSTS 仅研究用途、维基 CC BY-SA 有相同方式共享义务——均**不得作为对外宣称的学术比对库**，仅内部基准与种子语料；用户上传文档必须脱敏 + 授权。
6. **【已知坑】PyInstaller 打包**：体积大 + 杀软误报（Windows 常见）；用 onedir 模式 + 提交白名单规避；Nuitka 作为发布期优化项。
7. **【待核实】paper-generate-check-system**：公开 GitHub 检索无此仓库，请向用户核实准确 URL。
8. **【校准冷启动】回传样本稀疏**：校内试点几百人，前 1-2 个月配对样本可能 <50；必须有"规则+常数偏移"冷启动兜底，避免模型空转。
